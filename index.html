Agent workspaces on Coder

Every agent runs in its own ephemeral, governed Coder workspace on its own branch. Model keys stay in the Coder AI Gateway; workspaces only get short-lived, repository-scoped tokens.

02 · FORGE → SENTINEL

Plan, then stop at the gate

FORGE writes PLAN.md and halts. No code is written until SENTINEL approves the plan with a single-use approval that cannot be replayed.

03 · FORGE

Build in an isolated workspace

FORGE implements the approved plan segment by segment with conventional commits and runs the suite. The workspace holds zero LLM keys and zero raw credentials.

04 · SENTINEL

Review adversarially

SENTINEL reviews the diff read-only, on a different model provider if you like, and verifies by running tests in FORGE’s workspace through the audited A2A relay.

05 · VESSEL

Merge only when it is safe

VESSEL squash-merges only when the PR is approved, conflict-free and CI-green. Conflicts and failing checks go back to the same FORGE worker, context intact.

Keep the paper trail

After the merge, LORE records an Architecture Decision Record and updates the changelog, so anyone can reconstruct why the change was made.

How it works

Six handoffs. Every one on the record.

Each issue moves through the same declared flow. Every stage has an owner, a gate and an artifact you can inspect.

01 / 06NEXUS

Triage and assign

You open a GitHub issue. NEXUS syncs it into a typed ticket and hands it to an idle FORGE worker in its own fresh Coder workspace.

02 / 06FORGE → SENTINEL

Plan, then stop at the gate

FORGE writes PLAN.md and halts. No code is written until SENTINEL approves the plan with a single-use approval that cannot be replayed.

Quick start

From zero to your first merged PR.

One script creates the GitHub App, starts Coder and Redis, configures the model, pushes templates and connects your repository. Re-run it any time; it skips what is done.

  1. 01
    Run the setup script

    Published images or release binaries on Linux and macOS, or compile from source.

  2. 02
    Open a GitHub issue

    NEXUS picks it up on the next cycle and assigns a worker.

  3. 03
    Review the pull request

    Approve the gates that need a human. The team does the rest.

FAQ

Questions, answered.

OpenFlows is the orchestration layer that sits on top of your Coder environment. Five specialized agents - NEXUS, FORGE, SENTINEL, VESSEL, and LORE - collaborate through a Redis-backed state machine to take GitHub issues all the way to merged, documented pull requests. Coder governs where agents run; OpenFlows governs how they coordinate.

Coder is the infrastructure layer - it manages your development environments, workspaces, and compute. OpenFlows is the application layer - it orchestrates AI agents on top of Coder so your engineering team can focus on architecture instead of implementation. Together they give you a safe, secure, auditable, and governed SDLC.

No. Your team stays focused on architecture - creating issues, setting priorities, and reviewing specs. The agentic dev team handles implementation, review, testing, merging, and documentation autonomously within your governed Coder environment.

SENTINEL is ephemeral - spawned fresh for each evaluation with no accumulated bias. It reviews FORGE's plan before any code is written, evaluates every segment after commit against 5 criteria, and performs a holistic final review before any PR is opened. Every review is logged and auditable.

VESSEL detects conflicts early via GitHub's mergeable field before CI completes. It attempts automated rebase and resolution, and if needed, routes the conflict back to FORGE through a rework loop - no new branches required.

Yes. OpenFlows is fully open source. You can inspect the code, contribute, and self-host on your own Coder environment. The entire agent orchestration system is transparent and auditable.

NEXUS discovers GitHub issues and assigns them to FORGE. FORGE writes a plan, which SENTINEL reviews. After approval, FORGE implements code segment by segment with SENTINEL evaluating each one. VESSEL handles CI and merging, then LORE documents everything. NEXUS picks the next ticket and the cycle repeats - all coordinated, governed, and auditable from end to end.
