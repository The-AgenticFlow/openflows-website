System Design

Openflows is built as an asynchronous, event-driven system in Rust. Here's how the components fit together.

Core Components

ComponentTechnologyPurpose
DaemonTokio runtimeOrchestrates all agent processes
Agent RuntimeAsync tasksRuns each agent in its own task
GitHub ClientoctocrabInteracts with GitHub API
LLM Interfaceasync-openaiCommunicates with language models
Knowledge StoreSQLite + RedisPersists agent memory and context
Web ServerAxumExposes REST API and webhooks

Data Flow

A typical workflow follows this sequence:

  1. Input — GitHub webhook (new issue) or manual trigger arrives at the web server
  2. NEXUS Triage — The coordinator agent reads the issue, evaluates priority, and creates a task
  3. Task Queue — The task is placed on the appropriate agent queue (FORGE for code tasks)
  4. FORGE Execution — The builder agent clones the repo, reads context, writes code, and opens a PR
  5. SENTINEL Review — The reviewer agent checks the PR for correctness, style, and security
  6. LORE Recording — The historian stores decisions and patterns for future sessions
  7. Merge/Feedback — Approved PRs are merged; feedback on rejections feeds back to FORGE

Design Principles

  • Agent autonomy — Each agent operates independently within its permission boundaries
  • Event-driven — Actions are triggered by events, not polling
  • Graceful degradation — If one agent fails, the system continues operating
  • Human-in-the-loop — Review gates ensure human oversight for critical paths
  • Idempotent operations — Re-processing the same event produces the same result
