System Design

OpenFlows is built as an async, event-driven system in Rust using the PocketFlow engine - a directed graph where agents are nodes that communicate through a typed SharedStore.

Core Components

ComponentTechnologyPurpose
Flow Enginepocketflow-core (Tokio)Routes work between agent nodes via typed Actions
SharedStoreIn-memory / Redis (fred)Central state machine - tickets, worker_slots, pending_prs
GitHub ClientMCP + REST (reqwest)Issue discovery, PR creation, CI polling, merging
LLM Clientagent-client (reqwest)Anthropic, OpenAI, Gemini, Fireworks, Groq with fallback
Pair Harnesspair-harnessGit worktree lifecycle, process spawning, file locking
TUIopenflows-tui (ratatui)Setup wizard, live dashboard, doctor diagnostics

Data Flow

A typical issue-to-merge cycle follows this sequence:

  1. NEXUS polls GitHub - discovers open issues, syncs them as typed tickets into SharedStore
  2. NEXUS assigns - matches ticket to an idle FORGE worker, updates worker_slots
  3. FORGE creates worktree - isolated Git branch (forge-1/T-001), writes PLAN.md
  4. SENTINEL reviews plan - writes CONTRACT.md (AGREED / CHANGES_REQUESTED)
  5. FORGE implements - segment by segment; after each commit SENTINEL writes segment-N-eval.md
  6. SENTINEL final review - writes final-review.md; APPROVED unblocks PR creation
  7. FORGE opens PR - via GitHub MCP; STATUS.json written with PR_OPENED
  8. VESSEL polls CI - 10s interval; detects conflicts early via mergeable field
  9. VESSEL merges - squash merge with ticket reference; emits ticket_merged
  10. LORE documents - writes ADR, updates CHANGELOG.md, commits via GitHub MCP
  11. NEXUS loops - picks next ticket or halts gracefully if no work remains

SharedStore Keys

KeyTypeDescription
ticketsMapAll tickets: open, assigned, in_progress, completed, merged
worker_slotsMapAll workers: idle, assigned, working, suspended, done
pending_prsVecPRs waiting for VESSEL to merge
flow_recoveryRecoveryStateDetected inconsistencies for NEXUS to resolve
event_ringRingBuffer (1000)Last 1000 events - powers TUI real-time monitoring

Design Principles

  • Isolated worktrees - each FORGE worker gets its own Git branch; no shared mutable state in the filesystem
  • Ephemeral reviewers - SENTINEL is spawned fresh per evaluation; no accumulated bias
  • Flow recovery - NEXUS detects and resumes broken pipeline phases on every cycle
  • Human-in-the-loop only when needed - CommandGate for dangerous commands; notifications only for spec ambiguity, security concerns, or resource limits
  • Dual-backend state - in-memory for dev/tests, Redis for production; zero config change required
