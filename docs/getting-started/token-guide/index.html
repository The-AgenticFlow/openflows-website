Token Guide

OpenFlows acts on GitHub through a real identity, not a shared token. When the team pushes a branch, opens a pull request, or comments on an issue, it does so as the tenant's linked GitHub identity, resolved through a scoped OAuth link. This page explains that model in user-facing terms.

No raw tokens in worker workspaces

This is the single most important fact about how OpenFlows authenticates: worker workspaces hold no raw repository credentials and no model keys. The working spaces where agents do their jobs are thin and disposable - they contain none of the secrets that would let an attacker - or a misbehaving agent - act on your behalf.

1The identity model

OpenFlows never relies on a shared token sitting inside a sandbox. Instead, identity works in two layers:

  • A scoped GitHub OAuth link per tenant. For each tenant, you link a real GitHub identity through OAuth in the Coder dashboard (or the OpenFlows control panel). This grants the team the scoped ability to read the repository, push branches, open pull requests, and comment on issues - attributable to that tenant's identity, not to a shared, mysterious account.
  • A real, attributable identity for every action. Every action an agent takes inherits a real identity through Coder's login and that scoped OAuth link. There are no shared, anonymous accounts. When something is merged or commented on, it is attributable and auditable.

2Where credentials live

Credentials are deliberately concentrated, not spread around:

  • The control plane is where model access and the coordination happen. Every AI call is routed centrally through the model gateway, so worker workspaces never hold a model key.
  • The orchestrator workspace is the one long-lived, trusted component that legitimately holds the credentials the workers never see. It runs the coordination loop and is the auditable place where trust is concentrated.
  • Worker workspaces hold none of this. They have no raw repository credentials, no model keys, and no secrets - only the repository checkout, the coordination surface, and their role's skills.

Why this keeps things safe

Remove the secrets from the sandbox and an entire class of "stolen key" attacks disappears. Trust is concentrated in a single auditable place, and everything else is disposable and keyless. See the Security Model page for the full picture.

3How it is set up

  1. Add a tenant for your repository (see First Issue Walkthrough).
  2. Complete GitHub OAuth for that tenant - link the real identity OpenFlows will act as.
  3. That scope follows the team from then on. No per-ticket token management is needed.

If a deeper topic (such as token-level configuration or troubleshooting) is not covered here, that is because the current documentation keeps the authentication model intentionally simple: a scoped OAuth link, real identity, and no raw tokens in workspaces.
