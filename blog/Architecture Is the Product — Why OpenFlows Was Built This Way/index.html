Architecture Is the Product — Why OpenFlows Was Built This Way

Architecture is the new product

Research
FlowsFather

Written by

FlowsFatherFounder
Listen to this articleListen to this article

"The code is cheap now. The decisions aren't."

— Assah Bismark, Architecture Is the New Product

How Good Teams Actually Ship

Walk into any mature engineering organization — the ones that ship at scale without catching fire — and you'll see the same pattern. Before a single line of code is written, there are architecture reviews. Design docs. Boundary definitions. Contracts between services. Failure mode analysis. The team agrees on what connects to what, where the edges are, and what happens when things break.

This isn't bureaucracy. It's how you avoid silos. It's how you make sure the recommendation engine can talk to the fraud scorer, the fraud scorer can talk to the event pipeline, and the event pipeline can keep running when any one of them goes down. Without that architecture, you get exactly what the article describes: "a whole machine-learning island, disconnected from enterprise systems." A collection of prototypes pretending to be a product.

The teams that last don't just write code. They define the architecture first, then build inside it. The code flows from the structure. Not the other way around.

This is how OpenFlows was designed to work — but for agents instead of humans.

The Problem AI Creates

AI writes code now. It scaffolds services, generates endpoints, wires up frontends, produces tests. The code itself is approaching commodity — which is exactly the danger the article warns about. When code is cheap, it's tempting to skip the architecture phase entirely. Why spend two weeks designing when a prototype appears in two days?

Because the prototype isn't the product. The architecture determines whether it's sustainable. The article documents a $1.2M chatbot that technically worked but was unusable at scale. The failure wasn't the model. It wasn't the data. It was the architecture. They had a working model with nowhere to put it.

Research on AI initiatives shows that poor data architecture alone can tank model accuracy by 40%. You can have the best model in the world and it'll produce garbage if the pipes feeding it are broken. Code can now be generated instantly, but the decisions about how things connect, what talks to what, where the boundaries are, what scales and what breaks — those decisions haven't gotten cheaper. They've gotten more important, because there's more code connecting to more things.

Software Has Two Halves

A software project is not just code. It is two things:

  1. Engineering — the architectural decisions: how components connect, where boundaries are drawn, how failure is handled, how state flows, how recovery works. This is what endures after every line of AI-generated code gets replaced or refactored.
  2. Code — the implementation that materializes those decisions. This is the commodity. This is what AI generates well.

Most AI tools target the second half. OpenFlows targets both — but starts from the first. Architecture goes in. Code comes out.

OpenFlows: An Architecture That Produces Software

This is the core idea: OpenFlows is not an AI that writes code. It is a well-defined architecture — the same kind that mature dev teams use to avoid silos and ship reliably — expressed as a system of coordinated agents. You give it an issue tracker (GitHub issues) and it produces working software, but it does so by operating within architectural constraints that prevent the exact failures the article describes.

The Team Structure — Not a Monolith, a Team

In a well-run engineering org, you don't have one person doing everything. You have an architecture that defines roles with clear boundaries: a product manager triages issues, an engineer implements, a reviewer validates, a release manager merges and deploys. Each role has defined inputs, defined outputs, and defined handoff points. That architecture is what prevents silos and ensures nothing falls through the cracks.

OpenFlows encodes this same discipline as a team of five agents, each with a defined role, defined inputs, and defined handoffs:

You create a GitHub issue → NEXUS assigns it → FORGE writes the code → SENTINEL reviews it → VESSEL merges it → LORE documents it

No agent works in isolation. No agent scribbles on shared state without going through the defined architecture. The same way a good engineering org prevents silos through architecture reviews and clear ownership boundaries, OpenFlows prevents agent silos through a declared flow graph and a structured shared store.

The Flow Graph — Architecture Before Execution

Before any code is written, before any LLM is invoked, the architecture is defined as a state machine called PocketFlow:

NEXUS (orchestrator) → FORGE-SENTINEL (builder pair) → VESSEL (merge gatekeeper)     ↑                                                     │     └─────────────────────────────────────────────────────┘

Every agent implements a Node trait with three phases:

  • prep() — read state, gather context. No mutation.
  • exec() — compute, call external services, run the LLM. No store access.
  • post() — write results, emit actions, route the flow.

The separation is deliberate. exec() has no access to the shared store because the decision to take information and the decision to commit it are different architectural moments. Conflating them is how you get agents that scribble on shared state mid-thought — the exact kind of unmanaged sprawl that produces siloed, disconnected systems.

Actions route the flow. work_assigned → FORGE. pr_opened → VESSEL. conflicts_detected → FORGE (the same worker, directly). The routing table is explicit and visible. The architecture is not emergent — it is declared, the same way a good engineering org declares service boundaries before writing implementation code.

Planning Against Architecture, Not Just Writing Code

This is where OpenFlows differs fundamentally from "give an AI agent a prompt and let it write code." The FORGE-SENTINEL pair doesn't just write code. It operates within a structured planning cycle:

  1. PLAN.md — FORGE reads the issue and writes an implementation plan
  2. CONTRACT.md — SENTINEL reviews the plan, approves or requests changes
  3. Segment implementation — FORGE implements one segment at a time, each evaluated by SENTINEL
  4. Final review — SENTINEL does a full review of the completed work
  5. PR creation — Only after passing review does code become a pull request

The agents plan against the architecture. The plan is reviewed against the architecture. The code is tested against the architecture. This mirrors how senior engineering teams work: you don't let someone push code without a design doc and a review. OpenFlows encodes that discipline so the agents operate the same way.

But there's something deeper happening than just following a checklist. FORGE and SENTINEL are adversarial by design — one builds, the other critiques. SENTINEL's job is to find flaws in FORGE's plan, challenge its assumptions, and demand revisions before implementation begins. Then it evaluates each segment of code as it's written, and finally conducts a full review before any PR is opened. This adversarial tension pushes both agents to a level of thinking and self-criticism that mirrors what you see in a strong engineering team: the builder anticipates the reviewer's concerns, the reviewer holds the builder to a standard neither would reach alone. The result is better than either agent would produce in isolation — the same way the best code reviews in a real team aren't rubber stamps, they're genuine pushback that makes the work sharper.

The Pair Harness — Separation of Concerns at the Agent Level

The article's strongest claim: "AI reduces difficulty in low-level tasks like boilerplate, but shifts difficulty to higher-level skills."

OpenFlows embodies this separation at every level. An agent in OpenFlows is not the LLM. It is not the CLI process. An agent is the combination of a CLI backend (the muscle) and a configuration harness (the brain). Forge and Nexus might both use claude as their CLI, but they are fundamentally different agents because their architectures — their personas, skills, hooks, permissions, and coordination protocols — are different.

The BackendConfig struct encapsulates what is backend-specific. The Provisioner translates generic agent configuration into backend-specific artifacts. The Node trait defines behavioral contracts. These are architectural decisions that make the system extensible in two independent dimensions — swap the engine, or grow the team — without coupling them.

This is the same pattern you see in well-architected companies: separation of concerns, defined interfaces, the ability to swap implementations without changing contracts. OpenFlows applies it to agents instead of services.

The Three Approaches, Reframed

The article describes three ways teams build:

  1. Architecture-first — design the structure, then build inside it. This is how mature dev teams operate at scale. Slow to start, but the system can absorb new requirements without a rewrite. Compliance and governance are part of the design from day one.
  2. Model-first — build the model, worry about integration later. Fast for prototypes, but you're gambling that it fits into a system that doesn't exist yet. This is how teams end up with disconnected AI islands.
  3. Feature-first — ship the feature, figure out the architecture later. Fastest to launch, but technical debt accumulates fast, the system becomes brittle, and compliance gets neglected. Most failed AI projects were feature-first.

OpenFlows is architecture-first by construction. The same way a mature engineering team defines service boundaries before writing implementation code, OpenFlows defines agent boundaries, state contracts, and failure recovery before any agent runs:

  • The flow graph is defined before any agent runs.
  • The state contracts (TicketStatus, WorkerStatus, StoreEvent) are typed and enforced — the same way a good API contract is typed and enforced.
  • The routing table is explicit: every action has exactly one destination.
  • Recovery is built into the reconciliation loop, not retrofitted.
  • The Node trait separates reading, computing, and writing into distinct phases — an architectural constraint, not a coding convention.
  • Planning and review are mandatory steps, not optional: FORGE plans, SENTINEL reviews, only then does code become a PR.

Engineering goes in. Software comes out.

Why This Matters Now

The original article claims that "AI can generate code against a spec, but it can't write the spec." We'd refine that. AI can write specs — the models are getting there, and they're improving fast. But architecture is not just about producing a spec once. It's about maintaining it, evolving it, living with the consequences of every decision across months and years of a system's life. Until agents can own that full lifecycle — not just draft a document, but steward the architecture as the system grows — humans remain in charge. Not because agents can't reason about architecture today, but because the responsibility for what a system becomes still belongs to the people who will maintain it tomorrow. OpenFlows is built with this stance: humans own the architecture, agents execute within it. As models and agents continue to improve, that boundary may shift — and we'll welcome that when it comes — but for now, the architecture is a human decision, and the code is where the agents deliver.

Big engineering teams have always known this. They don't let developers push code without architecture reviews, design docs, and defined boundaries — not because they enjoy process, but because they've learned the hard way that code without architecture becomes siloed, brittle, and impossible to scale. The code is cheap. The architecture is what actually ships.

OpenFlows was built with this understanding. It gives you a team of agents that operate the same way a well-run engineering team does: they work from your issue tracker (GitHub), they plan against a well-defined architecture, they review before merging, and they recover from failure automatically. The product is not the code the agents generate. The product is the architecture — the flow graph, the state machine, the contracts, the failure recovery, the separation of concerns, the extensible plugin system, the typed state store. The code that FORGE writes is one output of that architecture. It is not the architecture itself.

When you run OpenFlows, you're not running an AI that writes code. You're running an architecture that produces software. The engineering decisions — what to build, where to put it, how it all fits together, what happens when things break — are embedded in the system's design. The code that comes out is the result of those decisions being executed consistently, reliably, and recoverably.

The teams that build things that last in the AI era are the ones making the best decisions about what to build, where to put it, and how it all fits together. OpenFlows gives you those decisions as a system. Engineering goes in. Software comes out.

The code is the output. The architecture is the product.

For the original argument that shaped this thinking, read Architecture Is the New Product by Assah Bismark.
